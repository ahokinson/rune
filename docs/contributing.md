# Contributing

## Repo layout

```
packages/rune/   the engine
  src/           re-exported from src/index.ts
  cli/           the `rune` CLI (new / add / dev / build)
  templates/     project templates that `rune new` scaffolds from
  test/          bun:test suites (one per module area)
examples/        standalone games that depend on the engine via workspace:*
  shared/        reusable game-level code shared across examples
docs/            hand-authored guides + generated API reference (docs/api/)
```

This is a Bun workspace: the engine lives in `packages/rune`, and each game under `examples/` is a standalone project that depends on it via `workspace:*`.

## Setup

```sh
bun install                    # link the workspace
bun run build                  # build packages/rune's dist/ (examples resolve "@ahokinson/rune" through it)
bun test                       # run the engine test suite
bun run typecheck              # type-check the whole workspace
bun run check                  # Biome lint + format check (read-only)
bun run format                 # apply Biome formatting in place
```

Per-example run scripts:

```sh
bun run example:tomb           # play the dungeon-crawler FPS demo
bun run example:attack-surface # play the rotating threat-globe demo
bun run example:tamagotui      # raise the pixel-art virtual pet
bun run example:overworld      # play the side-scrolling platformer
bun run example:teapot         # spin the 3D mesh viewer
bun run example:git-3d         # visualize a git repo's history in 3D
```

## Conventions

Read [Conventions](conventions.md) — it's the style guide every rune codebase follows. The short version:

- **Full words over abbreviations** — `Vector2` not `Vec2`, `deltaMilliseconds` not `dt`.
- **Verb forms over agent-nouns** — `castRay()` not `Raycaster`.
- **File names don't repeat their directory** — `audio/context.ts`, not `audio/audioContext.ts`.
- **Engine vs. shared vs. game** — reusable primitives in `packages/rune/src/`; cross-example code in `examples/shared/`; specific effects stay example-side.
- **Import paths** — `@/*` alias for cross-module engine imports, never `../`; same-directory siblings use `./name`. Game code imports from `"@ahokinson/rune"`.
- **Fixed update vs. frame update** — gameplay/physics on the fixed step; `useUpdate` only for render-frame visuals.

Biome enforces 2-space indent, 120-col width, double quotes, semicolons "asNeeded". TypeScript is `strict` + `noImplicitOverride` + `noUncheckedIndexedAccess` + `verbatimModuleSyntax`.

## JSDoc

The engine uses `/** */` JSDoc comments on every exported symbol. TypeDoc reads these to generate the API reference. When you add or change a public export, add or update the JSDoc — describe what the symbol does, and use `@param` / `@returns` / `@example` where they help. See `packages/rune/src/math/vector2.ts` for the established style.

In-body `//` comments (algorithm notes inside function bodies) are fine as-is — they're implementation notes, not API docs.

## Regenerating the API reference

The `docs/api/` directory is generated by [TypeDoc](https://typedoc.org/) with [`typedoc-plugin-markdown`](https://github.com/tgreyuk/typedoc-plugin-markdown). Regenerate it after touching public exports:

```sh
bun run docs              # generate docs/api/
bun run docs:watch        # regenerate on change
```

The config is in `typedoc.json` at the repo root. The entry point is `packages/rune/src/index.ts` — only symbols re-exported from the barrel appear in the reference.

`docs/api/` is committed (so GitHub renders the full reference), not gitignored. Regenerate and commit it as part of any change to the public API.

## Adding a new engine module

1. Create the source files under `packages/rune/src/<module>/`.
2. Re-export the public symbols from `packages/rune/src/index.ts`.
3. Add `/** */` JSDoc to every export.
4. Write tests in `packages/rune/test/<topic>.test.ts`.
5. Run `bun run typecheck`, `bun run check`, `bun test`.
6. Run `bun run docs` to regenerate the API reference.
7. Add a `docs/modules/<module>.md` overview page.
8. Update `docs/index.md` to link the new module page.

## Adding a new example

1. Create `examples/<name>/` with `package.json` (depend on `@ahokinson/rune: workspace:*`, `@opentui/solid`, `@opentui/solid`, `solid-js`; scripts `dev`/`build` → `rune dev`/`rune build`).
2. Add a run script to the root `package.json`: `"example:<name>": "bun run --filter ./examples/<name> dev"`.
3. Write `docs/examples/<name>.md` and update `docs/examples/index.md`.
4. If the example demonstrates engine patterns worth calling out, update `docs/conventions.md` or the relevant `docs/concepts/` page.

## Releasing

`packages/rune` publishes to [GitHub Packages](https://npm.pkg.github.com) as `@ahokinson/rune`. To cut a release:

1. Bump `version` in `packages/rune/package.json`.
2. Commit the bump.
3. `git tag vX.Y.Z && git push --tags`.

Pushing the tag triggers the `publish` workflow, which builds and publishes the package automatically.

Note for local engine development: `packages/rune`'s public entry point (`"@ahokinson/rune"`) resolves through its built `dist/` output, not raw source — this is why `bun run build` is part of initial setup above, and why it needs re-running after changing `packages/rune/src` or `cli` before an example (or the workspace typecheck/test run) picks up the change through the package specifier. The engine's own colocated tests import via `@/*`/relative paths and are unaffected.
